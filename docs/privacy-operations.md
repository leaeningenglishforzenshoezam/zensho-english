# 保存・削除の運営手順

この手順とコードは検証ブランチ用。実ユーザーの削除は、本人から具体的な削除依頼を受け、対象を確認した場合だけ行う。開発テストで本番データを使わない。

## 運営者の基本作業

- 窓口 goimon.admin@gmail.com を週2回以上確認。本人確認ができた削除依頼は原則30日以内を目安に処理し、遅延時は連絡する。
- 問い合わせ記録は対応完了後1年以内に削除。法令対応・未解決案件は必要期間に限定。保存した添付資料、ゴミ箱、手動バックアップも整理する。
- Cron成功と失敗はCloudflareのWorkerの実行履歴で週1回確認。失敗時は原因を解消し次の実行で整理されることを確認する。
- 個人情報・Google sub・トークン・受付コード・SQL出力は公開リポジトリやチャットに貼らない。運営用の端末・メールへのアクセスを限定する。

## 保持期間

| 対象 | 方針 |
| --- | --- |
| 最新の学習記録・プロフィール | 本人からの削除依頼等まで。休眠だけで自動削除しない |
| save_revisions | 履歴作成から30日を過ぎたものを毎時17分UTCのCronで削除。通常30日＋最大約1時間、障害時は復旧後 |
| sessions | 発行から24時間で認証無効。期限切れ行をCronで削除 |
| 削除受付 | 発行から30日で無効、Cronで削除。再発行は旧コードを無効化 |
| 手動DBエクスポート | 不要になり次第、作成後30日以内に削除。アカウント削除時はその情報を含む不要な書き出しも削除 |
| 削除の復旧対策台帳 | 内部ID・処理日時のみをアクセス制限した運営用記録に30日保持 |
| 端末の学習記録・利用者のバックアップ | クラウドの処理では削除しない |

D1のTime Travelは基盤側の復旧機能であり、アプリ上の削除と同時消去ではない。プラン別の保持期間を管理画面・公式仕様で確認（最大30日）。復旧したDBをそのまま利用者へ公開しない。

## 削除依頼の受付と処理

1. 利用者にアカウント画面で受付コードを発行し、表示された内部アカウントID・コード・削除希望を窓口へ送ってもらう。ボタン操作だけでは正式なメール依頼にならない。
2. 学習データが復元できなくなること、端末の記録と本人のバックアップは残ることを説明し、依頼範囲と意思を確認する。全端末で学習を終了してログアウトし、完了連絡まで再ログインしないよう依頼する。本人の希望なくアカウント全体を消さない。
3. ログインできない利用者にはGoogleアカウントの復旧・再ログイン後のコード発行を案内する。ユーザー名・メール差出人・内部IDだけでは本人と断定しない。確認できなければ削除しない。パスワードや認証トークンは求めない。
4. `cloud-worker` で `node scripts/deletion-sql.mjs` を実行し、受付コードと内部IDを入力。これはSQLを表示するだけで通信・削除はしない。
5. Cloudflareの対象D1のConsoleで最初のSELECTを実行。ちょうど1件の内部IDと受付日時を確認する。0件なら期限切れ・再発行・入力間違いを確認し、コードを再発行してもらう。削除対象を曖昧な名前検索で補わない。
6. 確認済みの削除意思に基づき、表示されたDELETEを実行。単一DELETEがコード・期限・内部IDを再検証し、usersと紐づく全行をCASCADEで削除する。条件を削らない。
7. 続くSELECTのremaining_usersが0であることを確認。1なら削除されていないので完了連絡しない。削除した内部IDを使い、以下の残件数もすべて0であることを確認する。

```sql
-- CONFIRMED_USER_IDを、確認済みの英数字・ハイフンの内部IDに置換する。
SELECT 'saves' AS kind, count(*) AS remaining FROM saves WHERE user_id='CONFIRMED_USER_ID'
UNION ALL SELECT 'save_revisions', count(*) FROM save_revisions WHERE user_id='CONFIRMED_USER_ID'
UNION ALL SELECT 'user_profiles', count(*) FROM user_profiles WHERE user_id='CONFIRMED_USER_ID'
UNION ALL SELECT 'sessions', count(*) FROM sessions WHERE user_id='CONFIRMED_USER_ID'
UNION ALL SELECT 'deletion_requests', count(*) FROM deletion_requests WHERE user_id='CONFIRMED_USER_ID';
```

8. 内部ID・処理日時を非公開の復旧対策台帳へ記録し、完了を返信する。古い端末のログインは無効。再ログインした場合は新規内部IDになる。元の端末データを勝手にゲストや新アカウントへ移さない。
9. 端末内も削除したい場合は別途依頼を確認し、対象ブラウザー・アカウントを確認して案内する。localStorage.clear()を勧めない（ゲストや同じOriginの別サービスにも影響）。現状はアカウント別の端末削除UI未実装。

## 障害復旧

Time Travelや手動バックアップから戻す際はAPIの受付を一時停止する。復旧対策台帳の削除済み内部IDに対応するusers行を再削除し、紐づく各テーブルが0件になったことを確認する。全セッションも失効させ、期限超過の履歴を整理した後で再開する。削除情報を含むバックアップのコピーを新たに長期保存しない。

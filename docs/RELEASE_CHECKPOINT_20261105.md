## Implemented this session

### Safe draw rejection recovery

- A definite stale-revision/insufficient-balance response carries the exact operation ID and expected revision.
- The server rechecks the receipt **after** observing the state, so an identical concurrent request that has already committed returns its original items instead of a false rejection.
- The client clears a pending request only for a matching, certified 409 rejection. Network failures, unproved conflicts, mismatched responses, future revisions and generic errors keep the original request.
- A rejection never automatically draws again. The player chooses the count again after balance refresh.
- Reopening the page after a certified rejection no longer blocks initialization; it shows a Japanese notice. A lost successful response still resumes the original receipt, without spending again.
- `inventory_limit` is deliberately NOT classified as definitely uncommitted: a concurrent identical request could have drawn different items before persisting a result.
